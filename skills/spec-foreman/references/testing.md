# 共用測試契約與執行節奏

TDD 是產生測試的方式，專案套件是這些測試的累積；不是二選一。Code review 檢查程式與需求，不能替代執行測試。

## Spec／tickets 先約定的最小契約

- 公開測試邊界、關鍵行為／已知例子，以及未涵蓋的風險。
- 共用測試工具、測試／fixtures 位置與必要環境。
- `related`：每張 ticket 相關測試的選取方式／命令。
- `regression`：整合後必要回歸的選取方式／命令。
- `full`：全部票完成及 review 修正完成後的完整套件，包含適用 build／lint／typecheck。

從專案設定取得命令；spec 有契約就沿用，缺少就一次補齊並確認。不先寫完所有測試。若框架不支援選取，記錄理由後用最小可行套件替代，不能默默不跑。

## 測試是產品資產

Workers 遵循指定 tdd skill：一個行為測試 red → 最小實作 → 同一測試 green，再做下一切片。預期值來自 spec／已知例子，驗證公開行為；環境／harness 故障不是產品 red。

測試與可重用 helper／driver 納入專案 Git，後續票沿用、增補；部署交付物可仍是單檔，但測試留在來源 repository。測試輸出、截圖與執行 log 才放暫存。

離線、動畫、重設／中斷等驗收條件要寫成實際環境設定與 assertion，不用標籤或 passed 數量代替。特殊外部 driver 僅在共用套件確實無法覆蓋時使用，注明理由並盡量轉成共用測試。

## 三層節奏

1. **每票：** worker 跑 related，含新 red→green；不每票重跑所有昂貴端到端流程。
2. **同步／整合後：** worker 在包含最新 integration HEAD 的候選版本跑必要 regression；Main fast-forward 到相同版本時沿用這次结果，不再跑一遍。HEAD、環境或執行依據不同／可疑時才重跑受影響檢查。
3. **全部完成：** Main 在精確整合 HEAD 跑 full，再開始一次完整 review。Review 有修正則逐項跑相關測試／必要回歸，全部修正整合後再跑 full，才交 human validation。沒有程式或測試變更就沿用同版本 full 結果。

必要測試未發現、未跑或關鍵 skipped 都不是通過。未涵蓋但可由人類驗收的主觀項明確列出，不能把可自動檢查的必要行為藏到人工階段。

## 交件前：行為覆蓋自查

Worker 在 related／必要 regression 通過後、首次交件前，對照本票全部驗收條件與共用測試：

- 找到實際驗證該行為的 test／UI check 與 assertion；多條條件可共用測試。
- 問「錯誤實作是否也會通過？」核對預期值、必要邊界、拒絕操作與生命週期；測試名稱、標籤與 passed 數量不是覆蓋證據。例如「沒有可見地雷」不能證明「恰好 10 顆地雷」。
- 發現缺漏或過弱 assertion，先補強共用套件並實跑受影響測試；已有功能的補測如實記為回歸，不補造 red 歷史。

完成條件：必要行為都有能排除對應錯誤的實跑檢查；可交人類判斷的主觀項與真正無法執行的項目明列限制。必要測試缺失仍阻塞。Result 只附可定位的 test 名稱／UI check ID 或路徑與限制，不新增覆蓋表、逐條長報告或強制 mutation testing。Main 不事前代設計全部測試，也不例行重做這輪自查；有具體缺漏／矛盾才查細節。

## 精簡證據

命令、tested SHA、exit 與實際測試摘要是基本證據。成功輸出短摘要，完整 stdout 存 log；正常收件不要求逐切片表格、額外截图、內容 hashes 或複製 session。

Main 發現具體矛盾時才看必要 log／測試；優先修好共用測試，而不是再造補證包。TDD 先後／粒度偏差如實記錄，不補造歷史；一般流程偏差在功能驗證通過後由 Main 記錄並繼續。虛假聲明、必要測試缺失或使用者明訂的嚴格 TDD gate 則阻塞並求援。
